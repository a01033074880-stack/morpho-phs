## 1. 项目目标与一句话概括

**目标**：做一个基于“拓扑声学晶格”的实时音频插件——声音在一块二维蜂窝陀螺晶格上传播，晶格的拓扑边缘态让声音沿边缘单向绕行、绕过缺陷而几乎不反射；一个慢速可激介质（形态场）在晶格上演化并调制参数，产生持续变化的音色。插件既能当效果器（输入音频激励晶格），也能当乐器（MPE 激励）。

**一句话**：2 自由度陀螺蜂窝晶格（Chern 数非零）+ 显式、能量稳定的 ESAV-LF 积分器 + 保证能量不增的参数更新 ENPU + Barkley 可激介质控制层，用 C++20 多线程内核做成 JUCE 8 插件 **MORPHO-PHS**（乐器）与 **MORPHO-PHS FX**（效果），VST3 / CLAP / Standalone。

**硬性目标**：48 kHz 下 32×32 晶格（4096 自由度）在 i9-13900H 上稳定实时：块 128 时 0（或接近 0）次超时，块耗时 p99 ≤ 0.7 × 块预算（预算 = 20.83 µs/样本，即块 128 为 2666.7 µs）。**Phase 5 已在 i9 上达成**（四次势：FX 2 线程、乐器 3 线程，3 次重复 0/11250 超时，§6.5）；HQ 势只有 HQ-fast 3 线程接近达标（§8.1）。

**原始开题与现状的差别**（Phase 0 审计后修正）：原开题的“正方标量晶格拓扑边缘态”“μ≤0 即严格无源”“SSDG 无条件稳定”“Gray–Scott 慢场 + 正反馈闭环产生有机演化 / 1/f”等说法经审计不成立或需要改写，见 §3.1。

## 2. 物理与数值模型（专家速读版）

- **模型**：M q̈ = −Kq − ∇U(q) + G q̇ − D(q̇) q̇ + B u，输出 y = Bᵀ q̇。
  - 晶格：蜂窝格点，每格点 2 个自由度（平面位移）；K 为中心力弹簧（加接地 k₀）。
  - G = blockdiag(g_i J₂)：格点内陀螺（回旋）项，破坏时间反演对称 → 能带 Chern 数 [1,0,0,−1]，存在单向边缘态。
  - D = blockdiag((−μ_i + η_i|v_i|²) I₂)：Rayleigh 型阻尼；μ>0 为负阻（自激），η 饱和。
  - U：逐自由度凸势：四次势 α/4·s⁴，或 log-cosh（“HQ”）；插件中 HQ 用可向量化的凸近似 Û（K=3 的 sqrt 和式，HQ-fast）。
- **ESAV-LF 积分器**：蛙跳 + 逐自由度标量辅助变量（SAV，ψ ≈ √(2U+c₀)）+ 中心化回旋 + 滞后一步的阻尼速度 ⇒ 每格点只解一个 2×2 线性系统，**完全显式、无迭代**。
  - 定理 1：离散功率平衡是恒等式 E⁺−E⁻ = h·uᵀy − h·v̄ᵀDv̄（无条件）。
  - 定理 2：仅需线性 CFL γ = hω_max/2 < 1 时，能量下界为正；μ≤0 时离散无源（与振幅无关）。
  - 定理 3（ENPU）：任意可容许参数跳变后能量不增；定理 4：能量门控自激有界 Ẽ ≤ max(Ẽ₀, ρ·Ẽ_cap)。
  - 命题 5/6：多端口 MPE 功率可分计量；“能量防火墙”——任意控制层经钳位 + ENPU 改参数不破坏上述界。
  - 证明：`docs/theory_proofs.pdf`（英文）、`docs/theory_v1.md`（中文）。
- **ENPU 默认 = 变体 C（selective）**：对 g/μ/η 是精确空操作，对 m/α/β 严格保持能量不增并保持 SAV 一致；g/μ 在核内逐样本插值（Phase 4 决策 D1）。
- **控制层**：蜂窝图上的 Barkley 可激介质（可得螺旋波/靶波），每 64 样本一个控制 tick，经钳位映射调制 μ、g 等。
- **拓扑通道**（FX 模式）：干声/全频路径 ∥ 3 段 Chebyshev-II 带隙滤波器组 → 边缘源端口，L/R 在上/下游拾音。

## 3. 各阶段工作、决策与理由

### 3.1 Phase 0：研究与可行性审计（`reports/Phase0_研究审计报告.md`）
结论：**可做，但必须按修正后的版本做。** 关键发现（全部有数值/解析证据）：
1. 原文“每格点 1 个标量自由度的正方晶格”Chern 数恒为 0，无拓扑边缘态 → 改为 **蜂窝 2-DOF 陀螺晶格**（C=[1,0,0,−1]）或 Haldane 型标量蜂窝。
2. “μ≤0 ⇒ 无源”在参数调制下不成立：750 Hz 改 m、α 本身就是功率端口，任何精确积分器在 43 ms 内能量增长 19–32 倍（参数共振）→ 设计 **ENPU**。
3. 原文 SSDG 非无条件稳定：8×8、1000 组冲击发散 10.5%；RK4 33.9%；Verlet 32.1%；隐式中点-dG 0%；**ESAV-LF 0%**；10 000 组门槛 ESAV-LF 0 发散，原文 SSDG 11.9%。
4. 原文 Bernoulli 公式在 μ=0 处 0/0（无源模式 100% NaN）→ 用 φ₁ 函数的稳定形式（最大误差 1.6e-16）。
5. Cayley 变换是 H-正交而非欧氏正交，矩阵稠密：16×16 单核 128%，不可行。
6. “显式离散梯度”非新方法（Bilbao–Ducceschi–Zama JCP 2023 等）→ **论文新颖性重新定位**为“拓扑晶格 + 无条件能量稳定显式格式 + 无源参数调制 + 实时实现”。
7–9. Gray–Scott 在 16×16 上几乎全部消亡或冻结；声能只加在 u 上时 v≡0 不变；原文闭环是正反馈并锁死 → 控制层改为 **Barkley 可激介质**，耦合重新设计。
10. CPU：修正格式下 8×8 <2%、16×16 ≈5% 单核可达；32×32 需要多线程。
另：多条引用被误述，已核实并更正（见 Phase 0 报告 §1）。

### 3.2 Phase 1：理论与原型（`reports/Phase1_阶段报告.md`）
- 用户决策：2-DOF 陀螺蜂窝 + 显式 ESAV-LF + ENPU + Barkley 控制层 + 共享晶格多端口 MPE。
- 定理 1–4、命题 5–6 完整证明；sympy 恒等式 + mpmath 50 位验证；4×10 000 组随机极端压力测试 0 发散。
- 拓扑边缘输运在音频频段：方向性 +52～+55 dB，缺陷绕行透射损失 ≤ 0.003 dB。
- C++20 纯头文件核心 10/10 测试通过、处理循环零分配；16×16 四次势在 box 单核 31%（含控制层 34%）；**32×32 单线程不能实时**。
- 默认非线性势：四次势（快）；log-cosh 作为 HQ 选项。

### 3.3 Phase 2：多线程内核与对比实验（`reports/Phase2_阶段报告.md`）
- **EsavLFMT**：填充 CSR gather，每 32 格点一个 chunk，静态连续划分；**每样本一次屏障**；能量/功率部分和按奇偶双缓冲写入 per-chunk 槽，每线程按固定 chunk 顺序冗余求和 ⇒ **任意线程数逐位一致**，与单线程差恰好为 0；零分配。
- box 实测 32×32 f64 四次势 + 控制层（AVX2 构建，块 64）：1T 28.67 → 2T 16.96 → 4T 10.61 → 8T 7.81 µs/样本；AVX2 与 AVX-512 几乎无差（访存/延迟受限）。
- exp1：ESAV-LF 全部压力套件发散率 0，能量不变量漂移 ≤ 5e-13 dB；**诚实记录**：强非线性下谐波精度偏离参考（SNHR 低 37 dB）。
- exp2：带隙 1/2 方向性 +72～+90 dB，带隙 3 仅 +34～+38 dB；宽带演示只有 ±6 dB 的原因（鼓组仅 1.1% 能量落在带隙、无吸收边界时绕回、滤波器过渡带漏能）已查清，用边框吸收 + Cheby-II 带隙滤波器组修复到 +74.7 / −75.5 dB。
- exp3：耦合提高复杂度（MSE 0.001–0.015 → 1.9–2.05），但**不存在稳健的 1/f** → 产品描述改为“有界、持续的不规则性”。
- exp4：可微逆向设计**失败**（模态滤波器组基线在 3/3 目标上更好且快约 400 倍）→ 降级，插件改走“预设 + 宏”。
- ENPU A/B/C：推荐 C；块率参数阶跃本身比变体更重要（>12 kHz 能量 +8.3 dB）→ 引入核内子块插值。

### 3.4 Phase 3：JUCE 8 插件（`reports/Phase3_阶段报告.md`）
- JUCE 8.0.9 + clap-juce-extensions：VST3 / Standalone / CLAP + `morpho_cli`；pluginval strictness 10 通过（Linux, Xvfb）。
- 架构：消息线程构建新晶格，音频线程只做原子指针交换 + 256 样本交叉淡化；SPSC 事件队列；三缓冲快照给编辑器；processBlock 零分配、无锁。
- HQ-fast：Û(s)=Σₖ wₖ s²/(√(cₖ²+s²)+cₖ)，K=3；|s|≤10 时 |Û−logcosh| ≤ 1.25e-3；凸、非负 ⇒ 定理 1/2 原样成立；成本只比四次势多 3–23%（精确 HQ 为 2.7 倍）。
- 27 个工厂预设（`.morpho` JSON，8 个宏，覆盖语义）；63 个离线渲染全部有限、无削波；修复了乐器过轻（−54 dBFS）、Edge 下游削波（上下游 RMS 相差约 33 dB，正是拓扑隔离）和 5 个预设电平问题。
- box 插件级 CPU（块 128，FX HQ-fast L32）：3T 11.2、4T 9.11、6T 7.30、8T 6.16 µs/样本；8T 时 p99 常变差（spin 线程与 VM 争抢 CPU）。
- 插值：8 样本 g/μ 插值有 +2.42 dB 高频伪影，逐样本为 0 dB，CPU 差在噪声内（9.30 vs 9.49 µs）。

### 3.5 Phase 4：实时线程、双插件、预设 v2、授权（`reports/Phase4_阶段报告.md`）

实时线程改造（针对 i9 首测的问题，§6）：
- `rt_thread.hpp`：CPU 拓扑（Windows `GetLogicalProcessorInformationEx` + EfficiencyClass；Linux sysfs 拓扑 + `/sys/devices/cpu_core` 与 `cpu_atom`）、每个物理 P 核取一个逻辑线程（避开 SMT 兄弟）、`SetThreadGroupAffinity` / `pthread_setaffinity_np`、`MmcssScope`。
- **混合屏障** `HybridBarrier`：自旋 → yield → `std::atomic::wait`（futex / WaitOnAddress），参数可配；替代 Phase 3 的纯自旋屏障。
- **专用常驻线程池**（可选）：全部计算线程都是可绑核的池线程，调用方（宿主音频线程）只发布任务并等待 `done_`；或“调用方计算”模式。
- **自动线程数**：L≤16 → 1；否则 clamp(P 核数−1, 2, 6)（i9 → 5）。
- **自适应自旋**（本阶段新发现后加入）：宿主按块周期调用时，工作线程在块间休眠再唤醒的代价使中位数慢约 40%（box：不 paced 7.87 vs paced 10.85 µs/样本）。现在调用方跟踪块周期 EMA，工作线程空闲自旋 = clamp(1.25×周期, idle_spin, 10 ms)，调用方等待也按忙时 EMA 自旋。代价：宿主持续调用时工作核保持忙等（CPU 占用表现为满核）。
- **超订阅保护**：专用池 + 调用方 ≥ 逻辑 CPU 数时自动退回“调用方计算”；pcores 模式下工作线程多于 P 核时不再把两个线程钉在同一核上（改为软亲和 P 核集合）。这是在 box 上测到 8 个专用工作线程（8 vCPU）时 168 µs/样本（正常约 7）之后加的。
- **专用池时宿主线程阻塞等待**（`caller_pool_spin=false`，默认）：宿主线程只短暂自旋后阻塞，每块多一次唤醒，但少占一个 CPU。box 上有负载时，超订阅情形明显好转（5 线程 171 → 48.5 µs/样本，仍不达标），3–4 线程时超时反而略多，所以列为待决，i9 上用 `pin_mmcss_cspin` 变体对比。
- 插件默认：`pin=pset`（软亲和 P 核集合，多实例不互相钉死）、MMCSS 开、专用池；可用环境变量 `MORPHO_PHS_PIN / MORPHO_PHS_MMCSS / MORPHO_PHS_POOL` 覆盖。
- 基准 CLI：`--pin --mmcss --pool --threads N --paced --adaptive --caller-spin --load --barrier-spin-us --idle-spin-us`，输出中位数 / p99 / p99.9 / max / 超时数 / PASS·NEAR·FAIL。

### 6.2 Phase 3 代码在 i9 上的问题假设
1. 线程池线程没有亲和性，Windows 调度器会把工作线程放到 E 核（主频低、与 P 核不对称），每样本一次屏障被最慢线程拖住 → 线程数越多越可能落到 E 核 → 扩展非单调。
2. 纯自旋屏障：线程被抢占时其余线程空转直到时间片结束（Windows 默认 15.6 ms 量级）→ 40–100 ms 尖峰。
3. 工作线程普通优先级、无 MMCSS → 与宿主其它线程、系统线程竞争。
4. SMT 兄弟共享一个 P 核时两个计算线程互相拖慢。
Phase 4 的改造（§3.5）逐条针对这些假设；i9 复测结果见 §6.4：假设 3（无 MMCSS）得到支持；假设 1、2 只部分成立（绑核本身不够，纯自旋在“最佳性能”下反而最好）。

“最佳性能”使纯自旋的中位数下降约 15–45%、超时减少 20–70 倍；混合屏障收益小得多，5 线程甚至更差（单次测量，46.9 ms 尖峰）。Phase 3 的 i9 数据（“平衡”、不 paced、每配置 3 s、FX 四次势、块 128）最好是 2 线程 14/1125 次超时，其余 93–484 次；条件不同，只能看量级。

**关键结论**

1. **32×32 仍不能可靠实时**：块 128 没有任何一组 PASS（也没有 NEAR）。最好的是 Phase 3 式纯自旋 p3spin 4–6 线程：7–12/1500 次超时（0.5–0.8%），p99/预算 0.958–0.992，max 3.3–3.4 ms。中位数 11–14 µs/样本，低于 20.83 µs 预算，所以这是**尾部延迟问题，不是吞吐问题**：p99 块耗时约为中位数块耗时的 1.5–1.9 倍（例如 p3spin 4T：中位数 1440 µs，p99 2555 µs）。
2. **只绑核、不开 MMCSS（pin）最差**：L32 出现 89 ms（4T）、163 ms（6T 块 128）、183 ms（6T 块 64）、178 ms（6T 块 512）尖峰；L16 也有 13–56 ms 尖峰，12 组只有 1 组 PASS。6 线程时 CPU 集合包含逻辑 CPU 0（[10,8,6,4,2,0]），6T 最差；但 **3–5 线程不含 CPU 0 也有 13–89 ms 尖峰**，所以 CPU 0 不能单独解释。硬绑核后线程不能迁移，一旦所在核被同级或更高优先级的线程（或 DPC/ISR）占用，就只能等待。
3. **绑核 + MMCSS 让 16×16 完全达标**：pin_mmcss 与 pin_mmcss_caller 在块 128 和 512 上 3–6 线程全部 0 超时，p99/预算 ≤ 0.68，max ≤ 2.5 ms（块 128）。MMCSS 把 pin 的 50–180 ms 尖峰压到 L32 最多 13 ms（块 512）、块 128 最多 4.3 ms。
4. **但在 32×32 上，绑核 + MMCSS 不如不绑核的纯自旋**：pin_mmcss 最好 27–28 次（5/6T）、pin_mmcss_cspin 最好 20 次（6T）、pin_mmcss_caller 最好 26 次（6T）；3 线程时中位数 19–20 µs、几百次超时。这一族变体都是线程越多越好：3 线程时每个线程的计算量太大，块耗时中位数已接近预算。
5. **pset（软亲和到 P 核集合，当前插件默认）不比 pcores 好**：32×32 块 128、4–6 线程为 95–188 次超时，比 pin_mmcss 的 27–60 次差（只有 3 线程时 pset 的 208 次好于 pin_mmcss 的 581 次）；16×16 也只有 6/12 PASS。插件默认值需要重新决定（§8.2）。
6. **乐器模式更重**：inst_L32_pin_mmcss 中位数 16.5–25.7 µs，84–1112 次超时，比 FX 模式的 pin_mmcss 差一截。
7. **宿主线程等待方式**（§8.2 第 9 条）：pin_mmcss_cspin（宿主自旋）与 pin_mmcss（宿主阻塞）在 i9 上差别很小（5T 23 vs 27、6T 20 vs 28 次），3–4 线程时自旋略差。阻塞可以保留为默认。
8. **一个混淆因素（新发现）**：p3spin 是唯一使用纯自旋屏障的变体（`barrier_spin_us=1e6`）；其余 Phase 4 变体都是混合屏障（自旋 50 µs 后转 `WaitOnAddress`）。`*.json` 的 `barrier_os_waits` 显示，32×32 块 128 时混合屏障每次测量有 219–12,395 次 OS 等待（p3spin 为 0），每次唤醒都有调度延迟。所以“绑核 + MMCSS 不如 p3spin”可能有一部分来自屏障类型，而不是绑核本身。**“绑核 + MMCSS + 纯自旋屏障”这个组合还没测过**，是最直接的下一个实验。

**原因假设（尚未逐一验证）**

- **CPU 0 / 中断负载**：Windows 把大量 DPC/ISR 放在 CPU 0；6 线程的 pcores 集合包含 CPU 0。可用 xperf/WPA 或 LatencyMon 查看各核的 DPC/ISR 时间来验证；或把 CPU 0 从 P 核列表中排除再测。
- **每样本一次屏障**：块 128 = 每块 128 次全线程同步；每个样本的墙钟时间约 11–14 µs，屏障之间每个线程只有几 µs 计算（i9 单线程约 28 µs/样本，按线程数平分）。任一线程晚到几十 µs，整块就被拖延；超时是“偶发长尖峰叠加”的结果。
- **Windows 对硬绑核线程的调度**：硬亲和让线程无法迁移，所在核被占用时只能等；MMCSS 提高优先级后好很多，但 MMCSS 的调度器会在“Pro Audio”任务上做占空比限制（可能造成周期性停顿），对此尚无数据。
- **混合架构的频率与功耗状态**：“平衡”与“最佳性能”的巨大差异说明频率、C 状态或 Thread Director 有很大影响；E 核负载、P 核睿频降档、核间频率不一致都可能把最慢的线程变得更慢。本次没有记录实际频率和温度。

| P3 重配启停 | 256 次启停 / 15 s，1435 块，**无卡死**；按旧判据（≥ 1000 次）判 FAIL |
| P4 类插件 32×32 切换 | 20 次切换、1000 块，无卡死，PASS |

P3 平均每次启停循环约 **58.6 ms**（15 s / 256，含线程创建 + MMCSS 注册 + 少量块与随机间隔；box Linux 上约 1.2 ms）。这是 Windows 建线程与 `AvSetMmThreadCharacteristicsW` 的成本，不是卡死。Phase 5c 改判据：无卡死（看门狗不变）+ 至少 min(100, 10 × 每部分秒数) 次循环 + 单次循环 < 2 s，并输出每次循环与 `prepare()`（停 + 重启）的中位数 / p95 / 最大值；按新判据 i9 的 256 次（需要 100 次）通过。插件里一次重建（改晶格尺寸 / 线程数）在消息线程上，约 60 ms 的成本不影响音频线程。

#### 6.5.5 专用池卡死的根因与修复（Phase 5b）

- 位置：`EsavLFMT::process_block` 的专用池分支，调用方线程等待工作线程 t0 发布 `done_ = s`。旧代码：`while (done_.load() != s) hybrid_wait(done_, done_.load(), ...)`——**读了两次** `done_`。
- 竞态：t0 恰好在两次读之间写入 `s`，第二次读到的就是 `s`，于是调用方调用 `hybrid_wait(done_, s)`，意思是“等到 `done_` 不再等于 `s`”。而 `done_` 下次改变要等下一块，下一块又要等调用方返回，于是所有线程都睡在 `WaitOnAddress`/futex 上：**0 CPU 的死锁**，与 i9 上 16 分钟无输出的现象一致。`std::atomic::wait(old)` 的语义（Windows `WaitOnAddress` 与 Linux futex 一样）是“值 ≠ old 才返回、可伪唤醒”，所以比较值必须是调用方刚刚看到的那个值。
- 为什么 Phase 4 没暴露：这段代码自 Phase 4 就存在（`include_phase4` 第 196 行），但窗口只有几纳秒。Phase 5 给工作线程加了 MMCSS，`notify_all` 唤醒的高优先级工作线程可以在 `notify` 返回后立刻抢占普通优先级的调用方，正好落在两次读之间；块越短、唤醒越频繁越容易触发（第 1 轮 3T/4T 正常，第 2 轮 3T 后卡死）。
- 修复：只读一次，用读到的值作比较值：`for (d = done_.load(acquire); d != s; d = done_.load(acquire)) hybrid_wait(done_, d, ...)`。工作线程的 `seen` 从 0 开始（不再在启动时读 `seq_`，避免启动与第一块之间的同类窗口）。`stop_workers` 的顺序（先 `quit_` seq_cst，再 `seq_++`，再 `notify_all`）与睡眠计数器的 Dekker 配对经核查正确。
- 调用方计算池（插件默认）审计：它不等待 `done_`，只走块内纯自旋屏障与空闲等待；空闲等待用 `seen` 作比较值、屏障先读代号再 `fetch_add`，均无此竞态。唯一风险点是工作线程 `seen` 的初始化，已一并修正。
- 复现：在两次读之间注入 300 µs 睡眠（旧代码），压力测试 0 块即卡死；按新的插桩位置用旧等待逻辑，170 块后卡死；修复后同样的注入下不再卡死。
- 压力测试 `tests/test_phase5_stress.cpp`（Windows 上为 `morpho_stress.exe`）：P1 专用池极小块（1–8 样本）、P2 调用方计算池极小块、P3 反复 `prepare()` 重配（1–6 线程、caller/dedicated/auto、无绑定/CPU Sets、空闲自旋 0–50 µs 或 3.5 ms，且要求 ≥ 1000 次启停）、P4 类插件 32×32 块 128 切换线程数；看门狗 10 s 无进展即打印状态并以退出码 2 结束。`-DSTRESS_HOOKS` 版本在 6 个竞态点随机插入睡眠 / yield。box 结果（3 个种子，普通版 30 s/部分、插桩版 20 s/部分）全部通过，见 §5.5。

## 8. 未解决的问题

### 8.0 Phase 5 之后仍未解决的问题（Phase 5c，按重要性）
1. **HQ-exact 在 32×32 上不实时**：i9 上 1/2/3T 为 54–58 / 31.7–34.5 / 24.1–26.6 µs/样本，全部超出 20.83 µs 预算，加线程无法解决（3T 也只把 1T 的耗时降到约 45%）。Phase 5c 的处理是限制为 L ≤ 16（L32 时按 HQ-fast 运行并提示）。要在 L32 上提供“精确 log-cosh”，需要更便宜的凸近似（Padé / 有理近似，需凸性证明）或 float32 + 多速率。
2. **HQ-fast 32×32 余量不足**：Auto 3T 三轮共 1/11250 次超时，p99/预算 0.543–0.757（两轮 ≥ 0.7，判 FAIL）；2T 31 次超时。目前标“High CPU”，可用但不保证。
3. **乐器模式 2T 余量**：2T 只测到 1 轮（0/3750，p99/预算 0.626，离 0.7 只有约 10%），所以乐器 Auto 取 3T（0/11250，0.480）。若要省一个核，需要更多 2T 重复数据或乐器路径再优化。
4. **L16 HQ-exact**：Auto 2T 仍有 12/11250 次超时（最差 0.875），属于接近实时；1T 141 次超时。
5. **专用池**：卡死已修复，但 3–4T 仍有 22–60 次超时（调用方被 OS 唤醒，bOSw 191–485），保持非默认；宿主线程也在 CPU Set + MMCSS 时 3–4T 有 15–17 ms 尖峰（`p5_caller_cpuset_host`）——真实 DAW 的音频线程通常有 MMCSS，需要实机确认 2T 默认在 DAW 里是否同样干净。
6. **多实例**：每个实例的计算线程在宿主持续调用时块间自旋 3.5 ms、块内纯自旋；多个 32×32 实例会占满多个 P 核，尚未测量多实例下的 CPU 占用与超时。
7. **真实 DAW、Windows 上的 pluginval / clap-validator、macOS/AU** 仍未做（box 上 pluginval strictness 10 已通过）。
8. **功耗 / 温度遥测**：PL1 假设无法定论（§6.5.3），需要 HWiNFO / Intel PCM 记录。

### 8.1 混合 P/E 核上 32×32 的实时抖动（Phase 4 时最重要的问题；四次势已在 Phase 5 解决）
- **Phase 5c 最终状态（§6.5.1）**：i9 三轮数据确认，FX 四次势 2T 0/11250（最差 0.310）、3T 0/11250（0.408），乐器 3T 0/11250（0.480）。尾部问题的根因是 Phase 4 协议中块内进入 OS 等待（bOSw 4000+）与旧内核太慢，二者都已解决。剩余问题见 §8.0。
- **Phase 5 / 5b 更新（i9 已实测，§6.5）**：四次势下此问题在 i9 上已基本解决——模板内核 1T 4.67 µs/样本即 PASS（p99/预算 0.367），插件默认协议 2–4 线程 PASS（0.30–0.31，bOSw 0）。仍未决（Phase 5b 时）：只有 1 轮完整数据——Phase 5c 已补齐 3 轮；HQ 势在 L32 上的余量——已测（§8.0 第 1、2 条）；多实例与真实 DAW——仍未做。下面是 Phase 4 时的分析，保留作记录。
- 现状（2026-10-31 i9 复测，§6.4）：Phase 4 代码在“最佳性能”下，32×32 块 128 **没有任何配置 PASS**。最好的是 Phase 3 式纯自旋（p3spin 4–6 线程，7–12/1500 次超时，p99/预算 0.96–0.99）；绑核 + MMCSS 最好 20–28 次；插件默认 pset_mmcss 95–208 次；乐器模式 84–1112 次。中位数 11–14 µs/样本，低于 20.83 µs 预算：**是尾部延迟问题，不是吞吐问题**。16×16 用绑核 + MMCSS 时块 128/512 全部达标。
- 结构性难点：每个样本一次全线程屏障（48 kHz × 块内每样本），块 128 意味着每块 128 次同步；任一线程被抢占或落到慢核，整块都会拖延。屏障间的计算量很小（32×32 时每线程每样本约 1–2 µs），同步成本占比高。
- 已知取舍：
  - 自旋越久，延迟越低，但宿主持续调用时工作核全程忙等；多实例时会互相挤占。
  - 硬绑核（pcores）在多插件实例或宿主自身也绑核时可能冲突，所以插件默认软亲和（pset）。
  - MMCSS 提高优先级，但不能阻止被同优先级或更高优先级线程抢占，也不阻止 Windows 把线程放到 E 核（需亲和或 CPU sets）。
- i9 复测的新线索：只绑核不开 MMCSS 时出现 50–180 ms 尖峰（3–5 线程不含 CPU 0 时也有）；混合屏障在 32×32 每组有数百到上万次 OS 等待，而纯自旋没有；“最佳性能”比“平衡”好一个数量级。三者都指向“某个线程偶尔晚到”，而不是计算太慢。
- 可能的方向（尚未实施，Phase 5 待定）：每 k 个样本一次屏障的时空分块（需要 halo 交换与额外计算，k 受 CFL 与邻接传播限制）；把 32×32 做成 2× 降采样子晶格或分区异步耦合（会改变物理/能量证明）；把计算线程交给宿主的线程池（CLAP thread-pool 扩展、VST3 无标准方案）；SIMD 化 2×2 格点求解（box 上 AVX2≈AVX-512，说明主要受访存/同步限制，收益有限）。

### 8.2 其它未决事项（Phase 4 时的决策清单；Phase 5 已处理第 1、2、6、7、8、12 条）

## 9. 下一步计划与给专家的具体问题

### 9.0 Phase 6 候选（Phase 5c 结束时；均未实施，按专家建议整理，数字是假设，需要实测）
1. **float32 更激进的路径**：引擎已是 float32，候选是把 `energy()` 的 double 累加与 HQ 势的 expm1/log1p 也改为 float32 SIMD，并测是否仍逐位稳定、能量恒等式误差是否可接受；目标是 HQ-fast 32×32 2T 稳定、HQ-exact 32×32 进入预算。
2. **多速率晶格**（边缘全速 / 体态半速）：可能把 32×32 的计算量减半，但改变离散格式，需要新的无源性证明与听感评估。
3. **SSB 外差带隙注入**：声音设计功能（把宽带输入移进带隙，使单向边缘传播更可闻），与实时性无关，需要单独设计与听测。
4. **Padé / 有理近似的 HQ 势**：要证明凸性与 U(0)=0；若成立，可替代 HQ-exact 的 expm1 + log1p，解除 L ≤ 16 的限制。
5. **E-RSAV 预算版**（可上调 ψ）：Python 原型结果（钳位版只有 ±2 dB 量级，`p5_ersav_alias.json`）不支持“+25～+32 dB”的说法；预算版需要新的能量恒等式证明后再移植。
6. **多实例 CPU 占用**：测 2–4 个 32×32 实例同时运行时的 CPU 占用与超时，评估块间自旋 3.5 ms 的代价，必要时提供“省 CPU”模式（块间改阻塞等待）或宿主线程池（CLAP thread-pool）。
7. **功耗 / 温度遥测**：基准脚本可选地读取 HWiNFO / Intel PCM 的封装功耗、PL1/PL2 限制标志与温度，以定论 PL1 假设（§6.5.3）。
8. **真实 DAW 测试**（Reaper / Ableton / FL，多缓冲区、多实例）、Windows 上 pluginval 与 clap-validator。

1. **补测缺失的组合**：“绑核 + MMCSS + 纯自旋屏障”（`--pin pcores --mmcss 1 --pool dedicated --barrier-spin-us 1000000 --idle-spin-us 1000000`），以及排除 CPU 0 的 P 核列表；每配置跑更久（≥ 20 s）并重复 3 次，估计单次测量的波动（本次每配置只跑 1 次、4 s）。

3. **确定插件默认值**（§8.2 第 1、2、9 条）：倾向 16×16 默认 pcores + MMCSS；32×32 在找到稳定方案前标为“高负载 / 建议大缓冲”。
4. **算法层面减少同步次数**：评估“每 k 样本一次屏障”的时空分块（halo 宽度 k 的重复计算）与红黑/多色划分，以及它们对离散能量恒等式和逐位一致的影响（§9.2 第 6、7 题）。
5. 之后再做 DAW 实机测试（多实例、不同缓冲区）、Windows 上的 pluginval 与 clap-validator。

### 9.2 想请教专家的问题
**实时音频 / Windows 调度**
0. （i9 复测后新增，最想问）i9-13900H 上 32×32 每样本一次屏障，中位数只用了预算的 55–70%，但 4–6 线程的较好变体仍有 0.5–4% 的块超时（p99 约为中位数的 1.5–1.9 倍）。不绑核的纯自旋反而比“绑核 + MMCSS + 自旋 50 µs 后转 WaitOnAddress”更好；只绑核不开 MMCSS 会出现 50–180 ms 尖峰（不限于含 CPU 0 的情况）。这像是哪类问题？应该先用什么工具（WPA/xperf、LatencyMon、ETW 的 CSwitch / ReadyThread 事件）定位？
1. 在 Windows 11 + Intel 混合架构上，插件内部的计算线程池用 `SetThreadGroupAffinity`（硬亲和）还是 `SetThreadSelectedCpuSets`（CPU sets，软）更合适？与宿主（Ableton、Reaper、FL）自身的 MMCSS / 亲和设置会不会冲突？
2. 每样本一次屏障、每块约 128 次同步、每段计算 1–2 µs：是否有成熟的低抖动同步方案（例如按核轮询的单写者标志、序列锁式屏障、`WaitOnAddress` 与自旋的切换阈值）？业界插件（多线程物理建模、卷积）通常怎么做？
2b. i9 上“最佳性能”比“平衡”超时少 20–70 倍（纯自旋）。插件是否应该在运行时降低节能影响（例如 `SetThreadInformation(ThreadPowerThrottling)` 关闭 EcoQoS、`SetProcessInformation(ProcessPowerThrottling)`）？还是业界只靠用户设置电源模式？
3. 线程空闲时在块间自旋（占满核）是否可接受？有没有更省电但唤醒延迟仍低于约 50 µs 的方式（例如 `SetWaitableTimerEx` 高精度定时器、`timeBeginPeriod`、Thread Director 提示 `SetThreadInformation(ThreadPowerThrottling)`）？
4. MMCSS “Pro Audio” 对插件内部新建的线程是否合适，还是应使用宿主提供的音频工作组（如 Windows 的 Real-Time Work Queue / `RtwqJoinWorkQueue`、macOS 的 Audio Workgroups）？
5. CLAP 的 thread-pool 扩展是否值得做：在支持它的宿主里把每样本计算交给宿主线程池？

**数值方法 / 并行化**
6. 显式 ESAV-LF（蛙跳 + SAV）能否做每 k 样本一次同步的时空分块（halo 宽度 k 的重复计算），同时保留离散能量恒等式与逐位一致？是否有相关文献？
7. 对 4096 自由度、每格点 2×2 求解的显式格式，GPU 不现实（延迟）；在 CPU 上除了按行块划分，还有哪些划分能减少跨线程依赖（例如红黑/多色排序、子晶格异步耦合）而不破坏无源性？
8. log-cosh 的凸近似 Û（K=3 sqrt 和式）是否有更便宜且仍凸、U(0)=0 的形式（例如有理近似）可直接 SIMD？

**拓扑声学 / 声音设计**
9. 在 16×16–32×32 这样的小晶格上，带隙内能量占比很低（鼓组约 1%）：有没有更好的激励或拾音设计让“单向边缘传播”在宽带音乐信号上更可闻？
10. 我们的论文定位（拓扑晶格 + 无条件能量稳定显式格式 + 无源参数调制 + 实时实现）是否足够新颖？还应对比哪些工作？
